# PostgreSQL

Renox apps use SQLite by default. That's the right choice for an app on one server: no database
server to run, and backups are a file (or Litestream). Switch to PostgreSQL when the app
outgrows that:
- several app servers,
- lots of concurrent writes,
- or a managed database.

The code stays the same on both: models, the query builder, `renox::db::sql()`, auth, the queue,
the cache, the scheduler, `db:shell` and `migrate:*` all work on both databases.

## Starting a new app on PostgreSQL

```bash
rnx new toko --database postgres
createdb toko && createdb toko_test     # or edit the URLs in .env
cd toko
rnx serve
```

This does three things:
- turns on renox's `postgres` feature in `Cargo.toml`,
- sets `DATABASE_URL` in `.env`,
- sets `TEST_DATABASE_URL` in `.env` (see [Tests](#tests)).

`rnx make:migration` and `rnx make:model -m` then write PostgreSQL SQL: they read
`DATABASE_URL` to pick it.

## Switching an existing app

1. Turn on the feature in `Cargo.toml`:

   ```toml
   renox = { git = "https://github.com/arif-rachim/renox", features = ["postgres"] }
   ```

2. Point `DATABASE_URL` at the server:
   `DATABASE_URL=postgres://user:password@host:5432/toko`.
   `postgres://` and `postgresql://` URLs open a PostgreSQL pool; anything else is SQLite.
   `DATABASE_POOL_SIZE` (default 8) sets the pool size on both.

3. Make your migrations run on PostgreSQL. See [Migrations](#migrations) below. Renox's own tables
   (users, tokens, notifications, jobs, cache) already have PostgreSQL versions.

4. Run `my-app migrate`, then [copy the data](#moving-the-data) if the app already has some.

## Migrations

A migration file runs on every database unless there's a version for a specific one.
`renox::migrations!()` picks the right file when the migration runs:

| File | Used on |
|---|---|
| `20260101000000_create_produk.up.sql` | every database without its own version |
| `20260101000000_create_produk.postgres.up.sql` | PostgreSQL |
| `20260101000000_create_produk.sqlite.up.sql` | SQLite |

The same goes for `.down.sql`. A database-specific `up` without its own `down` falls back to the
plain `.down.sql`, which is usually a plain `DROP TABLE`. The plain `up` may be left out when
both databases have their own.

SQL that differs between the two:

| SQLite | PostgreSQL |
|---|---|
| `id INTEGER PRIMARY KEY AUTOINCREMENT` | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `INTEGER` (always 64-bit) | `BIGINT` for `i64` fields; `INTEGER` is 32-bit and won't read into an `i64` |
| `TEXT` for `DateTime` fields | `TIMESTAMPTZ` (and `TIMESTAMP`, `DATE`, `TIME` for the naive chrono types) |
| `INTEGER` 0/1 for `bool` fields | `BOOLEAN` |
| `BLOB` | `BYTEA` |
| `REAL` | `DOUBLE PRECISION` |

Plain `TEXT`, `NOT NULL`, `UNIQUE`, `REFERENCES … ON DELETE CASCADE`, `CREATE INDEX` and
`DROP TABLE` are the same on both.

Each migration runs in a transaction. `CREATE INDEX CONCURRENTLY` can't, so a migration that
uses it runs without one, statement by statement (so does one with a `-- renox:no-transaction`
line). Keep such a migration to that one change: if it fails halfway, what ran stays.

Several servers can run `migrate` at the same deploy: an advisory lock makes them take turns, and
the later ones find nothing left to do. `migrate:fresh` drops everything in the schema, including
enum types, sequences and functions (not what extensions created).

## Writing SQL that runs on both

- Always write `?` placeholders. On PostgreSQL they become `$1`, `$2`, … before the query is sent.
  A `?` inside a string, a quoted name or a comment is left alone. This means PostgreSQL's JSON
  operators `?`, `?|` and `?&` can't be written through `renox::db::sql()`: use `db.postgres()`
  and sqlx for those.
- Values bind with their own types on PostgreSQL:
  - `bool` as `BOOLEAN`,
  - `DateTime` as `TIMESTAMPTZ`,
  - `NaiveDate` as `DATE`,
  - and so on.

  `None` binds as an untyped `NULL`, so it fits any column.
- Results must match the Rust type exactly. On PostgreSQL:
  - `SUM` of a `BIGINT` is `NUMERIC`, so write `CAST(SUM(harga) AS BIGINT)` to read an `i64`;
  - `SELECT 1` is a 32-bit integer.

  `COUNT(*)` is a `BIGINT` on both.
- `where_like` / `where_op(col, "like", …)` ignore ASCII case on both: Renox sends `ILIKE` on
  PostgreSQL.
- Timestamps from `renox::db::now()` are kept to the microsecond, as PostgreSQL does, so a model you
  saved equals the row read back.
- For anything specific to one database, check `db.dialect()`, or reach sqlx directly through
  `db.sqlite()` / `db.postgres()`.

## Things that behave differently (on purpose)

- **Emails** are stored trimmed and lowercased (registration, `User::register`), and looked up
  the same way. Logins and password resets therefore ignore case on both databases. The
  PostgreSQL `users` table also has a unique index on `lower(email)`.
- **Queue workers** reserve jobs with `FOR UPDATE SKIP LOCKED`. Workers on several servers never
  take the same job, and they don't wait on each other.
- **Scheduled tasks** claim each run in the `cache` table before starting it. `serve` on several
  servers runs a task once, not once per server. `SCHEDULER=false` is no longer needed for that.

## Tests

`renox::testing::TestApp` (and every app booted with an in-memory SQLite URL) uses a new, empty
**schema** in `TEST_DATABASE_URL` when that variable is set to a PostgreSQL URL. It is read from
the environment or from `.env`. Tests stay isolated from each other and from your development
data.

```bash
TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/toko_test cargo test
```

The schemas (`renox_test_…`) are left behind for inspection. To drop them all, drop and recreate
the test database.

A quick local server for tests:

```bash
docker run -d --rm --name pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=toko_test \
  -p 5432:5432 postgres:17-alpine
```

## Moving the data

Migrations create the schema. The data is copied separately, once, while the app is in
maintenance mode:

1. `my-app down` on the old server, then copy `storage/app.db`.
2. Create the tables on PostgreSQL:
   `DATABASE_URL=postgres://… my-app migrate`.
3. Copy the rows. [pgloader](https://pgloader.io) does this in one step, and **data only** keeps
   the tables Renox created:

   ```
   LOAD DATABASE
     FROM sqlite:///path/to/app.db
     INTO postgresql://user:password@host/toko
   WITH data only, reset sequences, truncate
   EXCLUDING TABLE NAMES LIKE 'renox_migrations';
   ```

   Timestamps written by Renox are ISO 8601 text, which PostgreSQL reads into `TIMESTAMPTZ`.
   Booleans stored as 0/1 need a `CAST` rule if your tables have any.
4. Lowercase stored emails if some have capitals:
   `UPDATE users SET email = lower(email);`.
5. Point `DATABASE_URL` at PostgreSQL, deploy, then `my-app up`.

## Deploying

Timeouts keep a slow or unreachable database from holding requests: a query waits at most
`DATABASE_ACQUIRE_TIMEOUT` (5 s) for a connection, a statement runs at most
`DATABASE_STATEMENT_TIMEOUT` (30 s; `0` for no limit, e.g. for a long report job, or `SET
statement_timeout` in its transaction), and a request answers within `REQUEST_TIMEOUT` (60 s).

`rnx make:deploy` writes the same Dockerfile and systemd unit. Set `DATABASE_URL` to the
PostgreSQL server in the environment; the Dockerfile's SQLite default is only a fallback. Skip
the Litestream part of `deploy/README.md`, which is for SQLite; back up PostgreSQL with your
provider's backups or `pg_dump`.
